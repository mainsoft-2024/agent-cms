## 원문


The two reported layout failures are consistent with the code: **the preview-link dialog constrains the dialog box but not its intrinsic grid column**, and **the media detail panel gives itself a fixed width without constraining what its grid children can demand**. The invite complaint is also justified, but the checkout changed during the review: the original role screen fell back to a user-ID field; the latest version I inspected replaces it with a name/email picker. **Adding a pending role by email still isn’t the same as sending an invitation.** The managed-auth API supports both workflows, but the UI needs to distinguish them.

This is a static review, not a browser reproduction. Line references point to the code inspected; shared-component and role-screen lines shifted as the checkout changed. I did not modify any files, so the report is returned here rather than written to `.slash/workspace/review-ui-2026-11-22.md`.

**Legend:** A = raw API UX · B = layout · C = missing state or interaction. **P1** = broken, misleading, or risks losing work · **P2** = clearly lacking · **P3** = polish. Unless otherwise noted, paths are relative to `registry/cms/`.

## Roles and people — `cms-roles.tsx`

- **P1 · A — `:99–105, :160–183`**: The new picker can add a pending role grant by email; it does not send an invite. Separate **Add existing person**, **Grant on first sign-in**, and **Send invitation**. Show pending, sent, revoked, and expired states only where the backend supports them.
- **P1 · C — `:31–39`**: Create Role immediately writes a generated name and has `finally` but no visible error handler. Ask for the name first, preserve the input on error, and prevent duplicate submissions.
- **P2 · A — `:121–147`**: Permission headings are already localized; the issue is that the matrix doesn’t explain effective access. Show what Administrator grants, why a permission is managed in code, and that write/publish/delete imply read (`src/roles.ts:159–166`).
- **P2 · C — `:76–104, :121–147`**: Membership changes commit immediately while role settings are edited in place and saved separately. Mark unsaved settings and guard role switches; explicitly label membership changes as immediate.
- **P2 · C — `:173–190`**: Removing a person is a small icon action. Add confirmation for admin/self-removal, a clear success message, and a recovery path when the server blocks removal of the last admin (`src/roles.ts:263–269`).
- **P2 · B — `:50–69, :129–150`**: A fixed-width role list competes with a four-operation matrix at tablet widths. Keep wide-table scrolling local with a visible cue, and use expandable permission groups on phones.
- **P3 · C — `:51–68`**: The list shows member counts but has no role finder or starter templates. Add search and examples such as Viewer, Editor, and Publisher.

**API path:** Use `client.searchUsers()` → `GET /roles/_users?q=` for existing people (`src/client.ts:448–454`, `src/http.ts:972–982`). The merged search includes the app adapter, sign-in identities, and people seen by the CMS (`src/roles.ts:135–145, :273–277`); don’t gate it on `roles().users`, which only reflects the custom adapter (`:200–204`). For managed accounts, `GET /users` returns people, invitations, policy, and mail availability; `POST /users/invite` accepts emails and returns per-recipient `sent` and `link`, with resend/revoke routes alongside it (`src/auth/index.ts:1027–1074`). Those routes require configured managed auth (`src/http.ts:408–412`); the docs CMS handler uses `resolveUser` instead (`apps/docs/app/api/cms/[...path]/route.ts:9–20`). Don’t offer “Send invitation” on that host unless it gains an actual invite integration.

## Recommended order

1. **Fix the reported clipping first.** Apply the bounded dialog and panel tracks, switch side panels based on available width, and test both exact user journeys with long signed URLs and filenames. The new `e2e/layout.spec.ts:171–203` is a good start; assert that the detail panel actually opened (its current click failure is swallowed), seed a fixture without relying solely on optional storage configuration, and explicitly assert that Copy and Close are reachable.
2. **Finish people management as a workflow, not a field replacement.** Support name/email search, make pending first-sign-in role grants unmistakable, and expose real invitations only on hosts that support them. Test same-name people, no matches, failed sends, disabled mail, and Korean keyboard composition.
3. **Fix misleading and stale states before visual polish.** Prioritize release preflight failures shown as clean, stale file actions, draft recovery, silent last-valid JSON saves, and the command palette’s direct publish. Then improve the automation builder, folder picker, and audit labels.
4. **Use a shared acceptance matrix.** Check 1600px, tablets, 390px/320px phones, short viewports, zoom, Korean, keyboard-only operation, and dark mode. In each layout, verify the primary action is visible, reachable, and still operates on the item shown.
