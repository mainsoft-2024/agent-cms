## 7. 예약 게시와 예약 숨김

**무엇을, 왜.** 출시 글을 미리 써 두고 정한 시각에 내보낸다. 지금은 그 시각에 사람이 눌러야 한다.

**데이터.** `cms_documents`에 `publish_at`, `unpublish_at`, `scheduled_by`, `scheduled_version`.

**동작.**

- 예약은 "그 시각의 최신 버전"이 아니라 **예약한 순간의 버전**을 게시한다. 예약 뒤에 누가 초안을 고쳐도 검토하지 않은 내용이 나가지 않는다. 예약 뒤에 고쳤으면 편집 화면이 알려 주고 다시 예약할 수 있게 한다.
- 실행 직전에 진단을 다시 돌린다. 오류가 있으면 게시하지 않고 감사 로그에 실패를 남기며 이벤트를 낸다 (웹훅과 자동화가 받을 수 있다).
- 예약에는 게시 권한이 필요하다. 예약한 사람이 그 뒤 권한을 잃어도 예약은 실행된다 (예약 시점에 승인된 것으로 본다). 감사 로그에는 예약한 사람과 실행 시각이 함께 남는다.
- 시각은 화면에서 `createCms({ timeZone })`의 시간대로 보여 주고 UTC로 저장한다.
- 실행은 1분 단위다. 크론이 5분마다 돌면 최대 5분 늦는다. 이 한계를 문서에 적는다.

**API와 도구.** `POST /collections/:c/:slug/schedule { publishAt, unpublishAt, expectedVersion }`, `DELETE .../schedule`. 도구 `schedule_document`, `unschedule_document` (publish 범위). `cms.runScheduled({ now })`.

**화면.** 시안 1번 (게시 버튼의 예약 창), 5번 (목록의 "예약됨" 탭과 배지).

## 19. 소프트 삭제와 휴지통

**무엇을, 왜.** 지금은 삭제하면 문서와 버전이 바로 사라진다. 에이전트가 삭제 권한을 갖는 제품에서 되살릴 길이 없는 것은 위험하다. 0.8.0에서 미룬 파일 휴지통도 여기서 함께 한다.

**데이터.** `cms_documents`와 `cms_assets`에 `deleted_at`, `deleted_by*`.

**동작.**

- 삭제는 휴지통으로 보낸다. 30일 뒤 영구 삭제한다 (`trash: { days: 30 }`, 0이면 지금처럼 바로 삭제).
- 휴지통에 있는 문서는 읽기, 목록, 검색, 에이전트 도구 어디에도 나오지 않는다. 공개 화면에서는 404다.
- 주소(슬러그)는 휴지통에 있는 동안 비워 주지 않는다. 복구했을 때 충돌하지 않게 하기 위해서다. 같은 주소로 새 문서를 만들려 하면 "휴지통에 같은 주소의 문서가 있어요"라고 알려 준다.
- 파일은 저장소에서 지우지 않고 표시만 한다. 공개 주소는 영구 삭제 때까지 열린다 (저장소에 파일이 그대로 있으므로). 바로 막아야 하면 "영구 삭제"를 쓰라고 화면과 문서에 적는다.
- 복구하면 문서는 삭제 전 상태(초안, 게시됨)로 돌아간다. 게시됐던 문서는 복구와 동시에 다시 공개된다. 복구 확인 창이 이 사실을 알려 준다.
- 영구 삭제는 관리자와 admin 범위 키만 한다.

**API와 도구.** `GET /trash?kind=`, `POST /trash/_restore`, `POST /trash/_purge`. 도구 `list_trash`(read), `restore_from_trash`(publish). 영구 삭제는 도구로 내지 않는다.

**화면.** 시안 6번.

## 8. 검토 요청 흐름

**무엇을, 왜.** 에이전트가 쓴 글을 사람이 확인한 뒤에만 내보내고 싶은 컬렉션이 있다. 지금은 키에 publish 범위를 주지 않는 것으로만 막을 수 있고, "검토해 주세요"라는 상태가 없다.

**데이터.** `cms_documents`에 `review_state`(`none`, `requested`, `changes_requested`), `review_version`, `review_requested_by*`, `review_requested_at`, `review_note`. 승인한 사람과 시각은 버전 행(`cms_versions.approved_by*`, `approved_at`)에 남긴다.

**동작.**

- 컬렉션 설정 `review: { agents: "required" }`면 키로는 게시할 수 없고 (`review_required`), 대신 검토를 요청한다. `review: { everyone: "required" }`면 사람도 자기 글을 직접 게시할 수 없고 다른 사람의 승인이 필요하다.
- 검토 요청 뒤 문서가 바뀌면 요청은 새 버전으로 옮겨 간다 (예전 버전을 승인하는 일이 없게).
- "승인하고 게시"는 요청된 그 버전을 게시한다. "돌려보내기"는 메모와 함께 `changes_requested`로 바꾸고 이벤트를 낸다.
- 0.6.0의 "에이전트가 바꾼 곳" 표시(33번)와 함께 보인다. 검토자는 바뀐 곳을 하나씩 수락하거나 되돌린 뒤 승인한다.

**API와 도구.** `POST .../review/request { note }`, `POST .../review/approve { publish }`, `POST .../review/reject { note }`. 도구 `request_review`(write), `list_review_requests`(read). 승인과 돌려보내기는 도구로 내지 않는다 (사람의 일).

**화면.** 시안 2번 (검토 요청 알림 줄), 5번 (목록의 "검토 대기" 탭과 배지).

## 9. 편집 잠금 표시, 그리고 119. 실시간 공동 편집

**무엇을, 왜.** 지금은 두 사람이 같은 문서를 고치면 나중에 저장한 쪽이 충돌 화면(0.6.0의 합치기)을 본다. 누가 열고 있는지 미리 보이면 충돌이 줄고, 같이 고칠 수 있으면 충돌 자체가 없어진다. 사용자가 실시간 공동 편집을 로드맵에 넣었다.

두 단계로 만든다. 1단계만으로 시안 4번과 5번이 된다.

**1단계: 서버리스에서도 도는 방식.**

- 문서를 연 화면이 15초마다 "여기 있어요"를 보낸다 (`POST .../presence { cursor, selection }`). 45초 동안 소식이 없으면 사라진다. DB 표 `cms_presence`에 저장하므로 서버가 여러 대여도 된다.
- 다른 사람의 커서와 선택 영역을 편집기에 그린다. 에이전트가 문서를 고치는 중이면 에이전트도 같은 방식으로 보인다 (도구 호출이 presence를 남긴다).
- 누군가 저장하면 다른 사람의 화면이 2초 안에 알아채고(짧은 주기 조회), 겹치지 않는 변경은 0.6.0의 3-way 병합으로 자동으로 합친다. 겹치면 지금의 합치기 화면이 뜬다.
- 한계: 글자 단위로 실시간은 아니다. 상대가 저장(또는 자동 저장)해야 내 화면에 반영된다. 그래서 함께 편집 중일 때는 자동 저장 주기를 2초로 줄인다.
- 문서 목록에도 편집 중인 사람이 보인다 (시안 5번).

**2단계: 글자 단위 실시간 (선택 모듈).**

- `@mainsoft/agent-cms/realtime`. Yjs와 WebSocket을 쓴다. 단독 서버(115번)나 WebSocket을 열 수 있는 호스팅에서만 켠다.
- 켜면 1단계의 조회가 WebSocket으로 바뀌고, 입력이 글자 단위로 합쳐진다. 버전은 지금처럼 사람이 "저장"할 때만 만든다.
- 에이전트의 `patch_document`는 Yjs 문서에 같은 변경으로 들어가 사람의 화면에 바로 보인다.
- 이 모듈이 없어도 화면과 문구는 같다.

**데이터.** `cms_presence(document_id, actor, cursor, selection, seen_at)`. 2단계는 `cms_collab_state(document_id, state bytea)`.

**화면.** 시안 4번 (함께 편집), 5번 (목록의 편집 중 표시). 색은 사람마다 정해진 8색에서 ID로 고른다. 에이전트는 회색.

**확인하지 못한 것.** 1단계의 조회 주기가 서버리스 비용에 주는 부담. 구현할 때 문서 하나에 세 명이 한 시간 열어 둔 경우의 요청 수를 재서 README에 적는다.

## 34. 섹션에 붙는 댓글

**무엇을, 왜.** 검토자가 "여기를 고쳐 주세요"를 문서 밖(메신저)에 남기면 에이전트가 읽을 수 없다. 댓글이 문서에 붙어 있으면 사람도 에이전트도 읽고 고칠 수 있다.

**데이터.** `cms_comments(id, document_id, thread_id, anchor, quote, body, author*, created_at, resolved_at, resolved_by*)`.

**동작.**

- 댓글은 섹션(`splitSections()`의 앵커)과 인용한 글에 붙는다. 본문이 바뀌어 인용한 글이 사라지면 섹션에만 붙은 것으로 보이고, 섹션도 사라지면 "위치를 잃은 댓글"로 패널 맨 아래에 모인다.
- 답글은 한 단계만. 해결하면 "해결됨" 탭으로 간다.
- 서명된 미리보기 링크(0.6.0)로 들어온 외부 검토자도 댓글을 남길 수 있다 (링크를 만들 때 "댓글 허용"을 켠 경우). 이름을 한 번 묻는다.
- 에이전트는 댓글을 읽고, 고친 뒤 답글을 남기고, 해결할 수 있다.
- 댓글은 버전에 속하지 않는다. 문서에 속한다.

**API와 도구.** `GET/POST .../comments`, `POST .../comments/:id/resolve`. 도구 `list_comments`(read), `add_comment`(write), `resolve_comment`(write).

**화면.** 시안 3번.

## 111. 릴리스

**무엇을, 왜.** 출시 때는 글 하나가 아니라 공지, 안내서 수정, 예전 글 내리기가 한꺼번에 나가야 한다. 하나씩 누르면 중간 상태가 공개된다 (Strapi, Sanity).

**데이터.** `cms_releases(id, name, state, publish_at, created_by*, published_at)`, `cms_release_items(release_id, document_id, action, version)`. `action`은 `publish` 또는 `unpublish`.

**동작.**

- 릴리스에 문서와 할 일(게시, 게시 취소)을 담는다. 담는 순간의 버전이 고정된다. 문서를 더 고쳤으면 릴리스 화면에 "v5 → v7"처럼 보이고, 항목을 다시 담아 새 버전으로 바꿀 수 있다.
- "게시"는 한 트랜잭션이다. 하나라도 문제가 있으면(진단 오류, 권한, 버전 충돌) 아무것도 하지 않고 어떤 문서가 왜 막혔는지 보여 준다.
- 예약할 수 있다 (7번과 같은 실행기).
- 한 문서는 열려 있는 릴리스 하나에만 들어간다. 릴리스에 든 문서를 따로 게시하려 하면 알려 준다.
- 게시된 릴리스는 기록으로 남는다. 되돌리기는 만들지 않는다 (문서마다 버전 기록으로 되돌린다).

**API와 도구.** `GET/POST /releases`, `GET/PATCH/DELETE /releases/:id`, `POST /releases/:id/items`, `POST /releases/:id/publish`, `POST /releases/:id/schedule`. 도구 `list_releases`(read), `add_to_release`(write), `create_release`(write). 릴리스 게시는 도구로 내되 publish 범위가 필요하다 (`publish_release`).

**화면.** 시안 7번 (목록), 8번 (릴리스 하나).

## 46. 버전 이름표와 고정

`cms_versions`에 `label`, `pinned`. 버전 기록에서 이름을 붙이고 고정한다. 고정한 버전은 `versions.max`로 정리할 때 지우지 않는다. 릴리스로 게시된 버전에는 릴리스 이름이 자동으로 이름표로 붙는다. 도구 `label_version`(write).

## 35, 36, 37. 미리보기를 편집기와 잇기

- **35 (남은 부분).** 편집기의 커서가 있는 섹션과 미리보기의 같은 제목을 양방향으로 맞춘다. 앱의 컴포넌트로 미리보기를 그릴 수 있게 `renderBlocks(blocks, components)`를 `cms-parts`에서 내보낸다.
- **36.** `parseMarkdown`의 블록에 `line`, `endLine`을 남긴다. 미리보기의 블록을 누르면 편집기의 그 줄이 선택된다. 댓글의 인용, 진단의 "11번째 줄", 섹션 diff가 같은 좌표를 쓴다.
- **37.** `cms.preview(actor, col, input)`와 `POST /collections/:c/_preview`가 저장하지 않고 `{ blocks, toc, diagnostics, diff, publicUrl }`을 돌려준다. 어드민 미리보기와 에이전트의 저장 전 점검이 같은 코드를 쓴다. 도구 `preview_document`(read).

## 45. 붙여넣기 정규화

웹 페이지나 문서 프로그램에서 복사한 글을 붙이면 지원하는 마크다운으로 바꾼다 (제목, 목록, 굵게, 링크, 표, 코드). 보이지 않는 문자와 둥근 따옴표를 정리한다. 바꿀 수 없어 사라지는 것(색, 글꼴 크기)은 없애고, 붙여넣은 뒤 한 번 알려 준다. HTML을 마크다운으로 바꾸는 라이브러리는 `turndown`을 쓴다 (화면 쪽 의존성).

## 48. 섹션 단위 편집기

본문을 `##` 단위 카드로 보여 주고 카드의 순서를 바꾸거나 사이에 끼워 넣는다. 묶음 4의 블록 본문(3번)과 같은 화면 문법을 쓰므로, 여기서는 "섹션 순서 바꾸기"만 먼저 넣고 블록 편집은 묶음 4에서 한다.

## 128. 저장된 필터

문서 목록의 검색어, 상태 탭, 분류, 작성자 조합에 이름을 붙여 저장한다. 사람마다 자기 것을 갖고, 관리자는 모두에게 보이는 것을 만들 수 있다. 표 `cms_saved_filters(id, collection, name, query jsonb, owner_id, shared)` (Payload query presets).

## 끝났다고 보는 기준

- 예약한 문서가 시각이 지나고 `/_cron`이 불리면 예약한 버전으로 게시된다. 그 사이 초안을 고쳐도 고친 내용은 나가지 않는다
- 삭제한 문서와 파일이 휴지통에 보이고, 복구하면 원래대로 돌아오며, 31일째에 영구 삭제된다 (시계를 돌려 테스트)
- 휴지통의 문서는 REST, 검색, 도구 어디에도 나오지 않는다
- `review: { agents: "required" }`인 컬렉션에서 publish 범위 키로 게시하면 `review_required`가 나오고, 사람이 승인하면 게시된다
- 브라우저 두 개로 같은 문서를 열면 서로의 표시와 커서가 보이고, 겹치지 않는 수정은 충돌 화면 없이 합쳐진다
- 에이전트가 `add_comment`로 남긴 댓글이 화면에 보이고, 사람이 남긴 댓글을 `list_comments`로 읽는다
- 릴리스의 문서 하나에 진단 오류가 있으면 아무것도 게시되지 않는다
- 미리보기의 제목을 누르면 편집기의 그 줄이 선택된다
- 접근성 검사(axe)가 새 화면 전부에서 통과한다
- 실제 화면을 시안 8개와 같은 크기로 찍어 비교한다
